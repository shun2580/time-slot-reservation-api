# 枠予約API 仕様(ドラフト)

## 目的
Go のバックエンド開発力(レイヤー設計・SQL・トランザクション・認可・テスト)を示すポートフォリオとして、時間枠の予約APIを作る。

## 題材
定員制のシェアスペース(コワーキングの1日利用など)の予約サービス。toC 向け。

- スペースは1か所だけ(スペースのテーブルは持たない)

## 登場人物と権限
| 役割 | できること |
|---|---|
| 管理者 | 枠の作成・公開・変更・閉じる・削除、代理取り消し(利用者への通知付き) |
| 利用者 | 空き枠を探す・予約する・自分の予約を取り消す・取り消した予約を再予約する |

- 管理者かどうかは Keycloak のロールで判定する(DB には持たない)
- 管理者は予約しない(取消のエンドポイントを管理者が呼ぶと代理取消になるため)

## 用語
| 用語 | 意味 |
|---|---|
| 閉じる | 枠を予約できない状態にする(状態の変更) |
| 削除 | 枠を物理削除する |
| 本人取消 | 利用者が自分の予約を取り消す(状態の変更) |
| 代理取消 | 管理者が利用者の予約を取り消す(状態の変更) |
| 有効な予約 | 状態が「有効」の予約。取り消し済みは含まない |

## 枠
- 1つの枠に複数の予約が入る(定員あり)
- 枠は開始日時・終了日時を持つ
- 時間が重なる枠も作成できる
- 予約締切は必須。枠の作成時に管理者が設定する
- 予約締切は開始時刻以前であること
- 閉じる:公開中の枠だけ閉じられる。有効な予約がある枠は閉じられない。閉じた枠は再び開けられない
- 削除:予約が一度も入っていない枠だけ物理削除できる(状態は問わない)。取り消し済みの予約しかない枠も削除できない
- 変更:下書き・公開中の枠のみ。予約が入っていなければ全項目を変更できる。予約が入っていれば、定員の増加と締切の延長のみ可(締切は開始時刻以前)

## 予約
- 予約は、公開中・締切前・定員未満の枠に対してのみ可能
- 定員の判定は「有効な予約」だけを毎回数える
- 同じ利用者が同じ枠を重複して予約できない
- 本人取消は開始の24時間前まで。過去の予約は取り消せない
- 取り消しはステータスの変更とする(行は消さない)
- 本人取消の後の再予約は、取り消し済みの行を有効に戻す UPDATE で行う
  - 再予約も新規予約と同じく、枠の行をロックしてから定員と締切を確かめる
- 代理取消された利用者は、同じ枠を再予約できない

## 代理取り消し
- 管理者が利用者の予約を取り消し、利用者にメールで通知する
- 有効な予約がある枠を閉じたい場合の逃げ道として使う

## 状態遷移

### 枠
| 状態 | 意味 |
|---|---|
| 下書き | 作成直後。利用者には見えず、予約できない |
| 公開 | 予約できる(締切前・定員未満の場合) |
| 閉じた | 予約できない。再び開けることはできない |

- 「締切後」「終了」は時刻から判定し、状態には持たない

| 操作 | 遷移 | 条件 |
|---|---|---|
| 作成 | → 下書き | 管理者 |
| 公開 | 下書き → 公開 | 管理者 |
| 閉じる | 公開 → 閉じた | 管理者。有効な予約がないこと |
| 削除 | (下書き・公開・閉じた)→ 物理削除 | 管理者。予約が一度も入っていないこと |
| 変更 | 下書き・公開(状態は変わらない) | 管理者。「## 枠」の変更の条件に従う |

### 予約
| 状態 | 意味 |
|---|---|
| 有効 | 予約中。定員の判定で数える |
| 本人取消 | 利用者が取り消した |
| 代理取消 | 管理者が取り消した(利用者にメールで通知) |

| 操作 | 遷移 | 条件 |
|---|---|---|
| 予約 | → 有効 | 利用者。枠が公開・締切前・定員未満 |
| 本人取消 | 有効 → 本人取消 | 本人。開始の24時間前まで |
| 再予約 | 本人取消 → 有効 | 本人。新規予約と同じ条件 |
| 代理取消 | 有効 → 代理取消 | 管理者。通知待ちを同じトランザクションで作成する |

- 代理取消 → 有効 の遷移はない

### 通知待ち
| 状態 | 意味 |
|---|---|
| 待ち | 送信前、または再送待ち(試行回数と次の送信時刻で表す) |
| 送信中 | 送信処理が確保した |
| 済み | 送信成功 |
| 失敗 | 再送の上限に達した、または一定時間「送信中」のまま止まった。ログを出す |

| 操作 | 遷移 |
|---|---|
| 作成 | → 待ち |
| 確保 | 待ち → 送信中 |
| 成功 | 送信中 → 済み |
| 失敗(上限未満) | 送信中 → 待ち(試行回数を増やし、次の送信時刻を設定) |
| 失敗(上限到達) | 送信中 → 失敗 |
| 停止の検知 | 送信中 → 失敗(一定時間経過) |

## 同時実行
- 予約・再予約・本人取消・代理取消・閉じる・削除・変更は、枠の行を悲観ロック(SELECT ... FOR UPDATE)してから処理する
- ロックの順番:必ず枠の行を先にロックし、予約の行はその後。全処理で統一する(デッドロック防止)
- 「定員未満か」の確認は、ロックを取った後、同じトランザクションの中で行う
- 同じ利用者の重複は (枠ID, 利用者ID) のユニーク制約でも防ぐ。制約違反は 409 に変換する

## 会員情報
- 構成:Keycloak + users テーブル
  - Keycloak:ログイン情報(メールアドレス・パスワード・ログイン状態)。メールアドレスの正本
  - users:Keycloak の利用者ID(sub)とアプリ固有の情報。メールアドレスは持たない
- users の行は初回アクセス時に作成する(管理者も同じ)
- 通知メールの宛先は、送信処理が Keycloak の管理APIから取得する
  - 送信処理は Keycloak にサービス用クライアントとして登録し、クライアントクレデンシャル方式でトークンを取得する

## 通知(メール)
- アウトボックス方式:代理取消と同じトランザクションで「通知待ち」の行を書く
- 送信処理は別プロセス(別コンテナ)で動かす
- 行の確保:SELECT ... FOR UPDATE SKIP LOCKED で行をロックし、「送信中」に更新して即コミット。メール送信はロックの外で行う
- 重複送信は許さない(送信前に「送信中」と記録する)
- 再送:初回の送信に失敗したら、再送は3回まで(最大で合計4回送る)。間隔は 1分 → 5分 → 15分。次に送る時刻を通知待ちの行に持つ
- 再送の上限に達したら「失敗」とし、失敗のログを出す(ログ監視でアラームを飛ばす想定)
- 10分以上「送信中」のまま止まった行は失敗として扱い、ログを出す(再送はしない)
- 失敗の記録:通知待ちの行にはエラーの種類だけを残す。詳しい内容はログに出し、メールアドレスは伏せる
- Keycloak から宛先を取得できない場合も、再送の対象とする
- 開発中は Mailpit でメールを受け止めて確認する

## 時刻
- 全て JST にそろえる(コンテナの TZ、MySQL のタイムゾーン、Go の DB 接続設定を明示する)
- 日時の列は DATETIME

## 認証・認可
- 認証:リソースサーバー方式。Keycloak が発行した JWT を検証するだけ(トークン発行APIは作らない)
- 認可:usecase 層で保証する
- 他人の予約を指定されたときは 404 を返す(存在を漏らさない)

## 空き枠の検索
- 条件:日付の範囲、空きがあるものだけ
- 既定で「公開中」かつ「締切前」のものだけを返す
- 「空きがある」は有効な予約の数を数えて判定する。件数が増えたときの SQL とインデックスの効き方は、実装後に EXPLAIN で確かめる

## 一覧のページング
- 件数(limit)と開始位置(offset)で指定する。limit の上限は100

## 入力の上限(仮の値)
- 枠の表示名:100文字まで
- 定員:1〜1000

## エンドポイント
- リソースは1つのパスで表し、誰が何をできるかは権限で分ける(管理者専用のパスは作らない)
- 状態を変える操作(公開・閉じる・取消)は専用のエンドポイントで表す
- `{id}` は API で見せる UUID

| メソッド | パス | 誰が | 内容 | 成功 |
|---|---|---|---|---|
| GET | `/slots` | 全員 | 枠の一覧。利用者には公開中・締切前の枠だけ、管理者には全状態の枠を返す(日付の範囲・空きありのみ・limit/offset) | 200 |
| POST | `/slots` | 管理者 | 枠の作成(下書き) | 201 |
| GET | `/slots/{id}` | 全員 | 枠の詳細。利用者が下書きの枠を指定したら 404 | 200 |
| PATCH | `/slots/{id}` | 管理者 | 枠の変更 | 204 |
| DELETE | `/slots/{id}` | 管理者 | 枠の削除 | 204 |
| POST | `/slots/{id}/publish` | 管理者 | 公開 | 204 |
| POST | `/slots/{id}/close` | 管理者 | 閉じる | 204 |
| GET | `/slots/{id}/reservations` | 管理者 | 枠の予約一覧(代理取消の判断用) | 200 |
| POST | `/slots/{id}/reservations` | 利用者 | 予約。本人取消済みなら再予約 | 201 |
| GET | `/reservations` | 利用者 | 自分の予約一覧 | 200 |
| GET | `/reservations/{id}` | 本人・管理者 | 予約の詳細。利用者が他人の予約を指定したら 404 | 200 |
| POST | `/reservations/{id}/cancel` | 本人・管理者 | 取消。利用者が呼ぶと本人取消、管理者が呼ぶと代理取消(通知付き) | 204 |
| GET | `/healthz` | 認証なし | 死活確認 | 200 |

- 利用者が管理者だけの操作を呼んだら 403
- 再予約は内部では UPDATE だが、利用者から見れば予約なので新規予約と同じ 201 を返す

## HTTPステータス
| コード | 意味 |
|---|---|
| 200 | 取得(GET)の成功 |
| 201 | 作成(POST)の成功 |
| 204 | 更新・削除(PATCH/DELETE)と、操作用の POST(取消・公開・閉じる)の成功 |
| 400 | パラメータ不足・不正値・バリデーションエラー |
| 401 | 認証失敗(未認証) |
| 403 | 権限不足(認証済み) |
| 404 | 対象が存在しない/他人の予約 |
| 409 | 現在の状態と衝突(状態が変われば成功しうる) |
| 422 | 規則に反する(送り直しても成功しない) |
| 500 | サーバー内部エラー |
| 503 | 一時的に利用不可 |

### 業務エラーの振り分け
| エラー | コード |
|---|---|
| 定員超過 | 409 |
| 同じ利用者の重複予約 | 409 |
| 有効な予約がある枠を閉じようとした | 409 |
| 締切後の予約 | 422 |
| 取り消し期限切れ | 422 |
| 代理取消された枠の再予約 | 422 |
| 閉じた枠への予約 | 422 |
| 予約が一度でも入った枠の削除 | 422 |
| 状態遷移として許されない操作(下書き以外の公開、公開以外を閉じる、閉じた枠の変更、取消済みの予約の取消など) | 422 |
| 予約がある枠で、定員の増加と締切の延長以外を変更しようとした | 422 |

- 業務エラーごとの `type` の値は api/openapi.yaml の冒頭に一覧がある

- エラー時の本文は RFC 9457(Problem Details)。`type` は業務エラーの種類ごとに用意する

## 構成
- Go / MySQL / Docker Compose(API・MySQL・Keycloak・Mailpit・送信処理)
- レイヤー分離(handler / usecase / repository / entity)
- 仕様は OpenAPI で先に書き、Swagger UI で試せるようにする
- テーブル定義は docs/time_slot_reservation_api_tables.md を参照
- OpenAPI の定義は api/openapi.yaml

## 技術の選定
- ルーティング:Go 標準の net/http(Go 1.22 以降のパスパラメータを使う)
- SQL:database/sql で手書きする
- マイグレーション:golang-migrate
- テスト用の MySQL:testcontainers-go
- ログ:log/slog の JSON 形式。リクエストごとにリクエストIDを付ける。メールアドレスなどの個人情報は伏せる

## テスト
- usecase の単体テスト
- MySQL を使った repository のテスト
- 同時予約の競合テスト
- 認証・認可のテスト(テスト内で署名したトークンを使う)

## 設計判断の記録

- 各判断の「理由」は、仕様を詰めるやり取りの中で出たもの。多くは提案を検討して採用した。面接で説明できるよう、理由を自分の言葉で言えるようにしておく

### 題材・範囲
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 定員制のシェアスペースにする | 1つの枠に複数の予約が入る題材にすると、定員を超えないための排他制御が必要になり、DB とトランザクションの設計力を示せる | 会議室・レンタルスペース(1枠1グループが普通で、ユニーク制約だけで足りてしまう) |
| 1つの枠に複数の予約が入る形にする | 同上 | 1件の予約で複数人が使う形 |
| REST で作り、gRPC は後から足す | 評価の中心は通信方式ではなく本体の設計。同じ usecase に入口を足せば、レイヤー分離が役立つことを示せる | 最初から gRPC |
| 画面は作らず OpenAPI + Swagger UI で試せるようにする | 評価してほしいのはバックエンド。画面を同時に作ると作業量が倍になる | Next.js の画面を同時に作る |

### 予約と枠のルール
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 定員の判定は有効な予約を毎回数える | 値の食い違いが起きない | 枠に予約数の列を持つ(更新漏れで実数とずれる危険) |
| 取り消しは状態の変更にする(行を消さない) | 予約の記録を残すため | 物理削除 |
| 再予約は取り消し済みの行を有効に戻す UPDATE にし、(枠, 利用者) のユニーク制約は残す | アプリのチェックは「全ての書き込みが枠のロックを取る」間しか正しくない。DB 制約は、ロックを取り忘れた処理や手作業の SQL に対する最後の防壁 | DB 制約を外し、アプリのチェックだけにする |
| 再予約も新規予約と同じく、ロックしてから定員と締切を確かめる | UPDATE でも実質は新しい予約。別の経路にすると定員超過がすり抜ける | 状態を戻すだけの UPDATE |
| 有効な予約がある枠は閉じられない | 利用者に取り消してもらってから閉じる流れの方が、運用上の問題が起きにくい | 閉じたら予約も自動で取り消す |
| 代理取消を用意する(通知付き) | 設備の故障など、利用者が取り消してくれないと閉じられない場合の逃げ道 | 逃げ道を作らない |
| 代理取消された利用者は同じ枠を再予約できない | 管理者が取り消した意図を尊重する。閉じるための取り消しの途中で再予約が入るのを防ぐ | 本人取消と同じく再予約できる |
| 枠の削除は、予約が一度も入っていない枠だけ | 枠の削除に巻き込んで予約を消すと、問い合わせ対応や不正調査の記録が管理者の操作で消える。個人データを減らす話は、保存期間のルールとして別に扱う | 取り消し済みの予約ごと削除する |
| 閉じた枠は再び開けられない | 状態遷移を一方向にして単純にする | 再び開けられる(締切を過ぎた枠の扱いなどが増える) |
| 予約がある枠の変更は、定員の増加と締切の延長のみ | 利用者に不利な変更をさせない | 常に変更できる(通知や整合性の扱いが重くなる) |
| 予約締切は必須 | 締切の既定値を決める必要がなくなり、判定が単純になる | 任意項目にする |

### 同時実行
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 予約・取消・閉じる・削除・変更は、枠の行を悲観ロックしてから処理する | 予約と閉じる・削除が同時に来ると、確認と実行の間に状態が変わる | ロックせずユニーク制約だけに頼る(閉じる・削除の競合は防げない) |
| ロックは必ず枠の行 → 予約の行の順に取る | 処理ごとに順番がばらつくとデッドロックが起きる | 処理ごとに必要な順で取る |
| 「定員未満か」はロックを取った後、同じトランザクションで確かめる | ロックの外で数えると、同時実行では意味がない | ロックの前に数える |

### API の形
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 管理者と利用者でパスを分けず、権限で操作を分ける | REST ではリソースを1つのパスで表す。認可は usecase 層で保証するので、分岐の置き場所もはっきりしている | `/admin` の下に管理者向けをまとめる(同じリソースが2つのパスになる) |
| 公開・閉じる・取消は専用のエンドポイントで表す | 操作ごとに条件と副作用(ロック、期限、履歴、通知)が違う。状態の変化を専用のエンドポイントで表すのは、実務の API でもよく使われる形 | PATCH で status を書き換える(処理の中で分岐が増え、定員の変更とも混ざる) |
| 本人取消と代理取消は1つのエンドポイントにまとめ、呼んだ人の権限で分ける | 「予約を取り消す」という操作は同じ。その代わり、管理者は予約しない前提を置く | 代理取消だけ別のエンドポイントにする |
| 枠の変更は PATCH | 一部の項目だけを変えるため(予約があれば定員と締切のみ) | PUT |

### エラーの返し方
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 409 は「状態が変われば成功しうる」、422 は「送り直しても成功しない」で振り分ける | 基準を1つにすると、エラーの割り当てが一貫する | エラーごとに個別に決める |
| 他人の予約を指定されたら 404 | 他人の予約が存在するかどうかを漏らさない | 403 |
| エラーの本文は RFC 9457 | 標準の形式に合わせる | 独自の形式 |

### 認証・会員情報
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 認証はリソースサーバー方式(Keycloak が発行し、API は検証だけ) | 認可サーバーの自作は作業量が大きく、安全性の穴を作りやすい。実務で一番多い形 | トークン発行を自作する |
| 会員情報は Keycloak + users。users にメールアドレスは持たない | メールアドレスの正本は Keycloak。users にも持つと同期の問題が出る | users にメールアドレスを持ち、リクエストごとに更新する |
| 管理者の判定は Keycloak のロール | 権限の正本を Keycloak に置き、DB を引かずに判定できる | users に管理者フラグを持つ |

### 通知
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| アウトボックス方式(取消と同じトランザクションで通知待ちを書き、別の処理が送る) | 取り消しと通知待ちが必ず一緒に確定し、通知が消えない | リクエスト内で送る(利用者を待たせる)/goroutine で送る(プロセスが落ちると通知が消え、ログも出ない) |
| 通知はコミット後に送る | トランザクションの中で送ると、送信後に処理が失敗した場合に「取り消されていないのに通知だけ届く」 | トランザクションの中で送る |
| 送信処理は別プロセス | API と独立して再起動・台数調整ができる(Laravel のキューワーカーと同じ考え方) | API と同じプロセスの goroutine |
| SKIP LOCKED で確保して即コミットし、送信はロックの外で行う | 送信中もロックを持つと、送信が遅いときにロックが長引く | 送信中もロックを持ち続ける |
| 重複送信は許さない(送信前に「送信中」と記録する) | 選んだ方針。代わりに、送信中にプロセスが落ちると通知は届かない。そのため止まった行は失敗として扱い、ログを出す | 重複を許して、消えないことを優先する |
| 再送は間隔を空ける | メールサーバーの一時的な障害を越えやすい | すぐ再送する |

### データの持ち方
| 判断 | 理由 | 採らなかった案 |
|---|---|---|
| 時刻は全て JST。コンテナ・MySQL・Go の設定で明示する | 国内のみの利用。ただし Docker のコンテナは既定で UTC なので、設定しないと判定が9時間ずれる | 保存は UTC、表示で JST に変換 |
| 日時の列は DATETIME | 書いた値がそのまま保存され、JST 統一と相性が良い | TIMESTAMP(接続の設定で表示が変わる。2038年まで) |
| 主キーは連番、API で見せる ID は別列の UUID | 連番はインデックスの効率が良い。外に見せる ID は推測されにくくする | 連番だけ/UUID だけ |
| 予約の状態の変化を履歴テーブルに残す | 再予約の UPDATE で上書きされる「いつ誰が取り消したか」を残すため | 予約の行に取り消し日時と操作者を持つ(再予約で上書きされる) |

### 既定値として決めたもの(Claude判断)
- 定石があり、後から変えても影響が小さいものは Claude が判断した。必要なら覆す

| 判断 | 理由 |
|---|---|
| 再送は初回＋3回(最大4回) | 「再送は3回まで」という方針を言葉どおりに解釈 |
| 再送の間隔は 1分 → 5分 → 15分 | 一時的な障害を越えやすい |
| 10分以上「送信中」なら止まったと見なす | 1回の送信にかかる時間より十分長い |
| 操作用の POST の成功は 204 | 更新は 204 という既存の方針にそろえる |
| API で見せる ID は UUID v4、CHAR(36) | 主キーではないので並び順(v7)は不要。調査のとき読みやすい |
| keycloak_sub は VARCHAR(255) | Keycloak の既定は UUID だが、仕様上は長さが決まっていない |
| 状態の列は VARCHAR＋CHECK 制約 | ENUM は値を足すたびにテーブル変更が要る。CHECK でも DB で値を守れる |
| 通知の失敗はエラーの種類だけを保存し、詳細はログに出してメールアドレスを伏せる | users にメールを持たない方針と矛盾させない |
| users・枠にその他の情報は今は持たない(枠は表示名のみ) | 必要になってから足す |
| 一覧は limit/offset でページング(上限100件) | 最小版では単純な方式で足りる |
| 枠の作成の二重送信は防がない | 管理者の操作で、下書きなら削除できる |
| 入力の上限は表示名100文字、定員1〜1000 | 仮の値。運用で変える |
| 退会は将来の課題 | 最小版の範囲外 |
| ルーティングは Go 標準の net/http | Go 1.22 以降で十分。依存を減らす |
| SQL は database/sql で手書き | ロードマップの「SQLを自分で書く」に合わせる |
| マイグレーションは golang-migrate | 定番で、SQL ファイルをそのまま管理できる |
| テスト用の MySQL は testcontainers-go | テストのたびに使い捨ての DB を立てられる |
| ログは log/slog の JSON 形式＋リクエストID | 標準ライブラリで足り、ログ監視と相性が良い |
| 閉じた枠への予約、予約が入った枠の削除、許されない状態遷移、変更できない項目の変更は 422 | いずれも状態が変わっても成功しない(409/422 の基準に従う) |
| 一覧の limit の既定は 20 | 上限100の範囲で、画面1枚分に収まる件数 |
| 一覧には全件数を返さない(items・limit・offset のみ) | 空き枠の検索で全件数を数えると、重い集計がもう1回増える |
| 枠には残りの席数(remaining)を含めて返す | 利用者が予約できるか判断するのに必要 |
| 予約の返却には枠の要約(表示名・開始・終了)を含める | 自分の予約一覧で、どの枠の予約か分かるように |
| 管理者向けの予約一覧では、利用者を Keycloak の利用者ID(sub)で示す | users には API で見せる ID がなく、メールアドレスも持たないため |
| 管理者が予約・自分の予約一覧を呼んだら 403 | 管理者は予約しない前提と合わせる |

## 実装時の解釈
仕様の曖昧な点を、第1段階の実装でどう読むかを決めた記録。R1・R4 は殿の裁定、他は将軍の裁定(S-30)で、軍師の推奨に従った。仕様と食い違うものではなく、読み方を決めたものである。

| ID | 論点 | 実装時の解釈 | 決定者 |
|----|------|--------------|--------|
| R1 | 「予約が入っている」の範囲(枠の変更・削除・閉じる) | 「予約が入っている」は、取消済みを含む全状態の予約行が1つでもあることを指す。削除の基準(一度も入っていない)と同じ基準にそろい、外部キーの RESTRICT とも向きが揃う。 | 殿(2026-10-25) |
| R2 | PATCH /slots/{id} の部分更新の本文の定め | 予約がある枠では、title・startAt・endAt のいずれかが本文にあれば 422 update-not-allowed とする。capacity・reservationDeadlineAt は現在値以上なら可(同値は無変更として通す)で、現在値より小さければ 422 とする。予約がない枠では全項目を変更できる。未知の項目は DisallowUnknownFields で 400 validation-error とする。null は 400 とする。 | 将軍(S-30) |
| R3 | 部分更新後の項目間の整合(start<end、deadline<=start) | 現在値と本文をマージした後の値で、FOR UPDATE で枠を取得した後に usecase で検証する。違反は 400 validation-error とし、errors[] に field と message を入れる。DB の CHECK は最後の防壁であり、通常は到達しない。DB の CHECK 違反を 500 で返してはならない。 | 将軍(S-30) |
| R4 | 枠一覧(GET /slots)の条件と「締切前」の境界 | 全条件は AND で組み合わせる。利用者は、基底条件を「published かつ 現在時刻 < 予約締切」とし、status の指定は無視する。管理者は基底条件なしで、status で絞れる。availableOnly=true は両者とも「残席>0」だけを足す(状態や締切は別軸)。from は start_at >= 、to は start_at < で比べる。日付のみは受けず date-time のみとする。from が to より後なら 400 とする。予約できるのは現在時刻 < 予約締切のときのみで、締切ちょうどは締切後とする。予約の判定(殿が書く部分)もこの境界に合わせる。 | 殿(2026-10-25) |
| R5 | remaining の式・型 | remaining = capacity − COUNT(status='active')。整数・非 null・0 以上(PATCH が減員を許さないので負にならない)。draft・closed や締切後の枠でも同じ式とする(予約できるかは status と締切の別軸)。作成直後は capacity と同じ。一覧は LEFT JOIN の集計1本で出し、N+1 にしない。 | 将軍(S-30) |
| R6 | 業務エラー以外の Problem Details の type | RFC 9457 の既定 about:blank とし、title は HTTP の理由句とする。400 は入力の誤りすべて(JSON 破損・不正パラメータを含む)を /problems/validation-error に統一する。ServeMux で一致しないパスは 404、パスは一致するがメソッドが不一致なら 405 と Allow ヘッダを、いずれも Problem Details で返す(ラッパを置く)。401 には WWW-Authenticate: Bearer を付ける。新しい type URI は作らない。 | 将軍(S-30) |
| R7 | ロールの置場とロールなしの扱い | realm ロール admin を、トークンの realm_access.roles から読む。admin がなければ利用者とする。realm_access が無い、または空のトークンは認証は通り(401 にしない)、管理者専用の操作で 403 とする。利用者用の別ロールは作らない。 | 将軍(S-30) |
| R8 | aud の期待値 | aud=slot-api とし、Keycloak 側は audience mapper で載せ、API は APP_JWT_AUDIENCE で照合する。 | 将軍(S-30) |
| R9 | JWT の検証と JWKS | issuer と JWKS URL は別の設定にする。JWT の検証は、kid で鍵を引き、use=sig かつ alg=RS256 の鍵だけを受ける(enc 鍵、および RS256 以外の alg では通らない)。署名・iss・aud・exp を検証する。JWKS を取れず検証不能なら 503、署名・iss・aud・exp の不正および未知の kid は 401 とする。起動時は Keycloak が未起動でも落とさず、遅延取得する。 | 将軍(S-30) |
| R10 | 初回アクセスでの users 行の作成 | UNIQUE(keycloak_sub) に任せる。INSERT ... ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id)、または INSERT IGNORE の後に SELECT で、競合しても同じ行 id を得る(SELECT の後に INSERT する二段にしない)。時刻はアプリが JST で明示的に入れる。認証済みの全リクエスト(管理者・501 ルートを含み、healthz を除く)で行う。2回目以降は updated_at を更新しない。middleware は repository を直接触らず、usecase のインターフェース経由で行う。 | 将軍(S-30) |
| R11 | エラーの優先順位と不正な {id} | 401(トークン)→ 403(ロール。DB を引かず usecase の冒頭)→ 400(本文・クエリの形式検証)→ 404(対象なし、利用者に見せない下書き)→ FOR UPDATE の後に 409/422 の順とする。path の {id} が UUID でなければ「存在しない」として 404 とする。 | 将軍(S-30) |
| R12 | 日時のオフセットと小数秒 | RFC 3339 でオフセットを持つ値は任意のオフセットで受け、Asia/Tokyo に換算して保存・返却する(返却は常に +09:00)。オフセットなしは 400 とする。小数秒は Go で Truncate(time.Second) してから検証・保存する(丸めに任せると、deadline<=start の検証と DB の値がずれうる)。過去日時の検査は仕様にないので足さない。tzdata は time/tzdata の取り込みで足りる。 | 将軍(S-30) |
| R13 | 公開(draft→published)のロック | 公開でも枠の行を FOR UPDATE でロックしてから状態を確かめる(他の遷移とそろえ、ロック順を統一する)。 | 将軍(S-30) |
| R14 | 第1段階の試験の範囲(業務エラー) | 枠の4種を各1件以上: 409 slot-has-active-reservations、422 slot-has-reservation-history・invalid-state-transition・update-not-allowed。予約行は testcontainers の中で SQL で直接挿入して前提を作る(予約の usecase はない)。予約系の6種(capacity-exceeded・already-reserved・reservation-deadline-passed・cancellation-deadline-passed・rebooking-not-allowed・slot-not-reservable)は殿が書く部分として対象外とする。 | 将軍(S-30) |
| R15 | .http の範囲 | 枠系の7本 + healthz + トークン取得(Keycloak のトークン endpoint を slot-api-client の directAccessGrants で)。予約系は 501 の確認例を1つずつ付けてもよいが必須にしない。パスワードは .env の値を参照し、.http に直書きしない。 | 将軍(S-30) |
| R16 | 一覧の並びと limit・offset | ORDER BY start_at ASC, id ASC とする。limit が範囲外・非整数、または offset が負なら 400 とする(openapi.yaml の schema どおり)。応答の limit・offset は実効値(既定は 20 と 0)。 | 将軍(S-30) |
| R17 | 501 ルートと認証の前後 | 認証 middleware は healthz 以外の全ルートに掛け、未認証は 401 を先に返す。認証済みなら役割に関係なく 501(about:blank、title は Not Implemented)を返す。管理者の取消が仕様の 403 でなく 501 になる件は、指示どおりで矛盾として扱わない。 | 将軍(S-30) |

- 第1段階では POST /reservations/{id}/cancel などの予約系ルートは、登録のみで 501 Not Implemented を Problem Details で返す(殿が実装する)。仕様書の「管理者が呼んだら 403」は殿が取消を実装するときに入れる。(殿の裁可 2026-10-25)
- Problem Details の errors[](field・message)は validation-error のときに返す。パス一致でメソッド不一致は 405 と Allow ヘッダを Problem Details で返す。(殿の指示 2026-10-25)
